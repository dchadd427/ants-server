# Replays

A match of this game is its starting data (the map, the seed, who plays, the teams) plus the orders that the players gave, turn by turn: the engine is deterministic, so the same data and the same orders give the same match on every machine. A replay file holds exactly that, and a few checks that say whether a machine plays it out the same way. `replay_tool` reads a file, plays the match again with no window, and lists every order with its time, its place and the types of the ants that got it.

**Built:** recording in the desktop game; the file; `replay_tool`; the game server keeps the matches that its rooms play (the browser's matches too) for up to 90 days and lists and gives them out, and lists the ones that run now and gives out each as far as it has gone ("On the game server" below); the site's pages of the match history (every match, one match with its stats and its replay, the matches that run now: "The match pages") and the player in the game page ("Watching a replay"); the stats that the replay pass keeps with every record (over time, activity, combat, ants and economy: "The stats of a replay pass"), shown on the match page as a band of highlights, "Over time" and "Activity"; computer players' matches saved by `bot_arena --save-replays`, which show in the same list ("Matches of computer players"). **Not built yet:** a seat's point of view, the match page's sections for combat and for ants and economy (their numbers are kept), and what only an event sink in the engine can tell (what caused each hit, which ant struck); this page says what exists.

## Recording a match

Every match that the desktop game plays is recorded while it is played: a game on your computer (alone or against computer players) and a match of a room, as its host or as a guest. Nothing is switched on, and recording changes nothing in the game: it only watches the orders that the engine is given and the ticks that it runs. The browser game records nothing, and it has no button for a file: a page has nowhere to keep one, and a file could not be watched without the game anyway. What a browser plays in a room is recorded by the game server, which keeps it ("On the game server").

- **The file** is named after the map and the date and time of your computer, for example `ants-TREASURE-20261006-143209.antsrep`, and is written when the match is over, into the folder `replays` beside the settings file: `~/Library/Application Support/Ants/Ants/replays/` on macOS, `~/.local/share/Ants/Ants/replays/` on Linux, `%APPDATA%\Ants\Ants\replays\` on Windows (with `--settings FILE`, the folder of that file; [`CONTROLS.md`](CONTROLS.md#settings)). The console says `Replay saved: <path>`. A file that is there is never replaced: a match that ends in the same second as another gets `-2` (then `-3`, and so on). The game never deletes anything from this folder, so it grows with every match that you play: clear it out when you like. A headless run without a settings file keeps nothing on disk.
- **A match that you leave** before it is over is kept as well, when something happened in it: you gave an order (the quit is one) or a minute went by. What the computer players or the other players did does not count, so a match that you walk away from in the first minute leaves nothing, however busy the others were. The file says that the match was not over. When a recording cannot be a file (a turn of a network match never arrived, or the file would pass 16 MiB), nothing is kept and the console says why.
- **Names:** in a game on your computer the file holds the names that were typed or given (a computer player's "Bot (Medium)", `--name`, `--team-name`, the name typed in the start menu); the name that the program makes of your system user stays out, because a file may be sent to someone. In a match of a room the names are the ones that the room showed everybody (the game server's own files leave out the words "Player" and "Player 1" to "Player 4": [`SERVER_REPLAYS.md`](SERVER_REPLAYS.md#replays), "Names"). A name in the file is plain ASCII, the letters from the space to the tilde: every byte of anything else becomes a `?` (a letter with an accent is two bytes and gives `??`), and a file whose texts hold anything else is refused when it is read.

To show someone a match, send the file. They need a build with the same `sim_rules` ("Watching a replay") and the same map; `replay_tool info FILE` says which.

What the game server keeps, the match history and the match pages are described in [their own page](private/REPLAYS_SERVER.md).

## Watching a replay

The pages are the site's own: the **Matches** link of the footer of the front page and the **Matches** button of [the bar at the top](SITE_NAV.md) (["The match pages"](private/REPLAYS_SERVER.md#the-match-pages); a new tab on the game page, so that a match being played there goes on, and on the front page while it holds a room ([`PLAY_IN_BROWSER.md`](PLAY_IN_BROWSER.md#your-room)); not shown while a replay is watched, whose header has "All matches") and the **player**, which is the game page opened as `/play?replay=<file>` (or `?live=<id>` for a match that is being played, below). Nothing is switched on and no account is needed.

- **The player** is the game itself in a replay mode (`--replay FILE`; the web page fetches `/replays/<file>`, writes it into the game's file system and starts the game with it). The game plays the match from the file on its own engine, shows the whole map (no Fog of War), and throws away every order of the HUD, so a visitor cannot change the match; the picture is for looking, not for clicking (**nothing can be picked**: no click, drag box, corner marks, Move and Stop buttons, order markers, ant voice, Ctrl+A / H / N / P or inspect panel; the pointer over it is the plain arrow, and the minimap, the edge of the screen and the wheel work as in a match: `HUD::set_view_only`, set for a replay alone). **Nobody writes in the chat of a recording or of a live match that is watched** (the same switch, `HUD::chat_writable`): the log is there to read, the input box is covered, there is no Send to button, and no typed text, Enter or quick chat key says anything. A watcher has no connection and no seat (a live match is a growing file, no new protocol), so nothing it could type would reach a player or the file, and it is never a line of the match; the lines it typed used to stand in its own log under the name of the first color. Above the picture: the map, the time, the players, and the buttons **All matches**, **Copy link**, **Stats** (when the server has a record of the match: "The match pages"), **Download** and **Fullscreen** (on a phone: **Matches**, **Copy link** as the share glyph alone, **Full** and the Menu). **Copy link** gives the address of the page that is watched, `/play?live=<id>` or `/play?replay=<file>` on this site and nothing else of the page's own address (a file of your own has no such button): where the page has a phone's layout (a window up to 700 px wide or 500 px high) and the browser has a share sheet it opens with that address, anywhere else the address goes to the clipboard and the toast says **Copied!**; a clipboard that refuses is tried with the browser's copy command, and when that fails too the browser's own box shows the address to copy by hand (the block `COPY_LINK_BEGIN` of `web/shell.html`). Under it: the timeline (click or drag to jump to a moment; the arrow keys jump 10 seconds, Home and End go to the ends) on a row of its own, with the activity curve above it ("The activity curve", below), and then, on the row under that, play and pause (the space bar too), **Back 30 seconds** right of it (a left-pointing double triangle with a small 30; a press jumps the playhead 30 seconds of game time back, never before the start, through the timeline's own jump, so a match that plays keeps playing, a paused one stays paused and the speed stays; it is not there for a match that is being played, `?live=`; a forward button and a shortcut key are not built; the page's half is `rewindControl` in `web/replay_page.js`), the time and the length, the **Auto camera / Manual camera** button ("The camera", below), the speed ½×, 1×, 2×, 4× and 8×, and a **Picture** button that opens a small window with the picture's dropdown (the table's seven shapes: the visitor's choice, remembered, the shape nearest the screen at first; [`PLAY_PICTURE.md`](PLAY_PICTURE.md#a-169-picture-that-fills-the-page)). The tag **REPLAY 1×** (or **Paused**, or the live words below) sits just above the bar, never over the picture (the bar's top margin makes the room: about 25 pixels, which a short window takes from the picture's height). A jump rebuilds the match from the start on the same engine (the game does it in slices, and a veil with a bar says "Jumping to 3:20…" when it takes a moment). At the end the game's own results screen shows and the play button becomes **Watch again**. In fullscreen the bar lies over the bottom of the picture, with the tag above its left end and a small tab on its top edge, and goes away by itself three seconds after the last touch of it (or the last move of the mouse) while the match plays (it stays while the match is paused); a swipe down on it (not on the timeline, which keeps its own drag) or a press of the chevron on the tab hides it for good ("Hiding the bar", below). **A finger on the picture never calls the bar**, so a tap or a drag of the map leaves the picture clear; a tap, or a swipe up, along the bottom edge calls it (a tap calls it in its click, so that it does not press the button that the bar then has under the finger; a strip about 56 pixels high with nothing drawn on it, there only while the bar is away and the last touch was a finger, so that a mouse keeps the game's edge; on a phone with gesture navigation the very bottom belongs to the system, and a touch that starts a little above it works). The first time in a visit that the bar goes away after a finger was used, a note says for 3 seconds how to bring it back. A mouse, a pen and the keys call it as ever.
- **The camera** (`include/ants_app/auto_camera.hpp`; a pure model that the application feeds while the recording plays: nothing of it reaches the simulation, so no hash moves). **Auto camera** (the default, lit) **locks on the biggest action and follows it**; **Manual camera** leaves the picture where the viewer put it. **What it reads** is what the engine already says while it plays, for every seat at once (a replay has no Fog of War; a world that had one would be read only where it is revealed): the hit points of the ants (a fall is a hit, an ant that is dead is a death) and the cues with a place (the blow of every kind of ant, which names the ant that struck, the dust ball of a brawl, a Thief diving into a hill and coming out, a hill's score going down or up, a Fire ant's beam and burst and the fire burning out, a bomb going off or picked up, a bomb taken to be defused, a base alarm and a raid, which the engine gives to the seat they are about and the camera places at that seat's hill, an ant falling in the water, a power-up dropping, a bridge going up, an ant picking food up). **The action score.** Every such event has a weight and fades away over 5 seconds: a kill 14, a bomb 10, a fire 5 for each of its two cues, a theft, a bomb taken to be defused or a hill losing points 6, a hit 2, a blow 1, banked food 2, the rest between 0.25 and 3 (food carried, a bridge and a power-up the least). An event of an ant belongs to the ant and moves with it. The score of a place is the sum of the events within seven tiles of it, and 12% more for every fighter after the first (up to 2.2 times) when ants of two sides or more are fighting there, so a team fight beats a lone scuffle with the same blows and a bigger event of one side only. **The lock.** The picture goes to the place with the most action once that has a score of 12 (a hit, a blow, a bomb or a fire alone does not; a kill with its hit does, and so does a brisk fight or a theft), centres on it and follows it: every tenth of a second the middle of the place is taken again from where its ants are now, so the picture goes along with a fight that moves. It stays at least 7 seconds; after that it moves on only to a place at least 1.5 times as busy as the watched one (and never for less than 1.5 times the score of 12: a fight that is cooling is not taken from by a place that has only just engaged), or lets go when the action it watches has been under a score of 3 for 3 seconds, and then stays where it is until something engages it again (when nothing happens nothing moves, and the first seconds of a match have the picture on the first hill). It never moves the zoom: a wheel zoom keeps Auto, at the viewer's zoom, and the picture glides back to the place. **How it moves.** A critically damped spring (about 0.6 s to arrive, at most 1400 world pixels a second, no snap, no overshoot), so a switch is one smooth pan, and a view that is still moving goes on from its speed. All its times are the viewer's seconds, not the match's: at 8× a place still holds for 7 seconds of looking, and from 4× up only the big events count (kills, thefts, fires, bombs). Every number is in the first block of `auto_camera.hpp`. The minimap shows a ring where the busiest place is now (the camera is there once it has locked on it; while a busier place begins during its 7 seconds the ring is already on the new place and the picture is not yet): whole while the camera is Auto, dashed while it is Manual. **Taking the camera** makes it Manual: the pointer at the edge of the screen or a drag on the minimap that moves the picture, and two fingers that pan it (more than 10 pixels within 300 ms: the pixel or two that a pinch drifts is not taking); the wheel and the pinch only zoom, which keeps Auto, at the viewer's zoom. The button returns to Auto: the picture glides to the busiest place now (else to the last thing that happened) and locks on it. The first time in a visit that the camera is taken a note says "You have the camera. Press Auto camera to follow the action again." The button's choice (not the taking) is remembered on the device (`localStorage` `ants.cam`, `auto` or `manual`). In the bar it sits between the clock and the speeds (the word goes where the bar is narrower than 900 px, and in fullscreen only the icon stays); on a phone it has a row under the speeds, which it shares with the Picture button. Page and game: `ReplayControl::SetCamera`, `ReplayValue::Camera` and `CameraTaken`; the page's half is `cameraControl` in `web/replay_page.js`. What the camera does **not** know: a moment before it starts (the picture arrives about a second after a fight begins, and a theft or a death at the very start of a match has nothing before it), where an order was aimed, or a seat's point of view (not built).
- **The page and the game talk through two exported functions** (`ants_replay_get(what)` and `ants_replay_do(what, value)`, the enums are in [`include/ants_app/replay_view.hpp`](../include/ants_app/replay_view.hpp)) and two calls of the game to the page (`window.antsReplayReport(info)`, what the file is or why it cannot be shown, and `window.antsReplayLeave()`). The state, the turn and the speed are the game's; the page only draws the bar.
- **A file that cannot be shown says why** on a card over the picture: recorded by an older version (it names both, and offers the file), recorded by a newer one ("Load the page again"), gone ("Matches are kept for 90 days"), or one that cannot be played (the map is missing, the file is damaged, the match does not play out the same here). A name in the address that is not the shape of the server's own file names is never fetched.
- **The same game in the same browser as ever:** **fullscreen holds the mouse (the pointer lock) as the game does** (same request on entering, same release on leaving or Esc, the same setting `ants.pointerlock`, the edges and corners of the picture scroll the map), and the bar stays clickable: the game's cursor is the pointer, and while it is over the visible bar the page makes the mouse events for what is under it (a press and release on a button click it, the timeline drags even beyond the bar) and draws a small arrow over the bar (the game's own cursor is under it); while the mouse is locked the bar lies inside the picture's box (on a screen of another shape than the picture's it would otherwise be partly out of the cursor's reach), the outermost pixels of the picture stay the game's (the edge scrolls with the bar up) and the wheel over the bar does not zoom. Known limits while locked: a button has no hover look, and the bar moves into the picture when the lock is taken or let go (a focused button loses its focus). Code: `barPointer` in `web/replay_page.js`. Leaving the page never asks "Leave the game?".
- **Hiding the bar** (fullscreen only: in a window the bar lies under the picture and covers nothing). The bar that lies over the picture has three states (`barZone` in `web/replay_page.js`, a small state machine that `tests/scripts/web_replay_bar_check.js` runs on a fake clock; the page's half is the glue in `web/shell.html`). **Open** is how a fullscreen page starts: the bar is up and, while the match plays, goes away by itself after a rest, as above. **Hidden** is the viewer's choice, made with the chevron on the bar's top edge (a tap, a click, Enter or Space on it), a swipe down on the bar, or the **B** key: the bar is not there at all (no look, no hit, no focus) and **nothing brings it back by chance**: not a move of the mouse, a click or a drag on the map or the minimap, the wheel, the edge scroll or another key. Only a thin **handle** stays at the bottom edge, a small chevron pointing up (44 px wide and 14 px high, centered, with an invisible hit area about 44 px high above it so that a finger finds it; nothing else lies over the picture: there is no element for the zone below). **Peek** is the bar called by the mouse: a mouse or a pen (never a finger: a finger has the handle) that RESTS for 150 ms (it moves by no more than 4 px) in the band of 48 px along the bottom of the picture, without its last pixels (at least 12 px, and on a larger picture the game's 5 px scroll strip as it lies on the screen, rounded up, plus 2 px: 17 px at three times the game's size, 25 px at 4K; the page reads the picture's rectangle, also for the cursor of a locked mouse), brings the bar up; a pass through the band that is shorter, a sweep along it (each move of more than 4 px starts the 150 ms again) or a drag with a button down calls nothing. Those last pixels are where the game scrolls the map: a pointer that rests there scrolls the map and never opens the bar. A peeking bar goes back to hidden by itself when the pointer has been away from the bar and the band for 700 ms (a button down, a drag on the timeline or the open Picture window counts as being on the bar), and the handle is gone while the bar is shown, open or peeking (one arrow only: the bar's chevron, which hides it again for good; the handle and its hit area never lie over the bar's controls). The handle (a button, there only while the bar is hidden: Tab to it, Enter or Space; a finger can also swipe up on it) and the **B** key bring the bar back to open, and B hides it again (B is ignored while a menu, a dialog such as the settings panel or the Picture window is open, or a field has the focus); the focus goes to the chevron when the bar is shown from the handle and to the handle when the bar that held the focus is hidden. `aria-expanded` is on the chevron (`false` while hidden) and the handle (always `false`: it is there only while the bar is hidden), the handle's name is "Show the bar", a hidden bar has `visibility: hidden`, the slide of the bar (and the fade) is off when the system asks for reduced motion, and the handle has system colors when forced colors are on. The choice is the page's for the visit (it is kept when fullscreen is left and entered again, and a peek ends with fullscreen); nothing is stored. A locked mouse (the usual state of a desktop fullscreen) presses the handle with the game's cursor as it presses the bar, and keeps a peeking bar open by being on it. A swipe down on the bar hides it for good (a tap on the handle, a swipe up on the handle or the B key bring it back), and the first time that a finger hides it the page says once how to bring it back (after a swipe down: tap the handle or swipe it up; when the bar went away by itself: swipe up from the bottom edge). Opt-in real-browser check: `tests/scripts/test_web_live.sh --only hide` (the chevron, the handle, a click, a drag and the wheel on the map, the other edges, a pass and a rest in the band, the leave time, the keys, a phone's taps, reduced motion).
- **A play** is counted by the game page (`web/replay_plays.js`, fetched only for a recording of the server's own store: never a live match, never a file of your own) after 10 seconds of "playing" (a pause, a jump, the end and a hidden tab add nothing; a gap between two looks adds at most a second), once a day for each recording in each browser (`localStorage` `ants.plays`, written before the play is sent; a browser that refuses it counts once for each page view), as a `POST /counts/play/<id>` with no body and no cookies; a 429 (the door's budget was used up) is tried once more a minute or so later, any other failure is not sent again. The replay page shows no count.
- **The screen stays on** while a recording plays or a live match is watched (and is let go on pause, at the end and at the results), through the browser's Screen Wake Lock: [`PLAY_IN_BROWSER.md`](PLAY_IN_BROWSER.md#the-screen-stays-on).
- **A match that is being played** is watched as a replay whose file is still growing: no new connection and no new protocol, only the public door ([`SERVER_REPLAYS.md`](SERVER_REPLAYS.md#replays)). The front page's list ("The match pages") reads `GET /live` every 5 seconds while it shows and lists each match from its start with a red **Live** mark and its length so far (**Starting…** until its first turn); **Watch** opens `/play?live=<id>`. The player gets `GET /live/<id>` (the recording so far), starts the game with `--replay --replay-live`, and every 2 seconds fetches the file again, writes it over the game's copy and calls `ants_replay_do(Extend)`; the game takes it when it is the same match with more turns and plays only up to 40 turns short of its end, so the picture of a match that is shown as it is is about 4 to 6 seconds behind the players. The server's header `X-Ants-Live` ([`SERVER_REPLAYS.md`](SERVER_REPLAYS.md#replays)) gives the page the turns the match had run, the turns shown and the delay, and with it the tag above the bar says **LIVE about 5 s behind** for a match shown as it is and **LIVE shown 30 seconds late** for one that two or more people play, or how far behind a paused or moved playhead is (**Paused · 0:36 behind**; a playhead that waited out a stop of the feed stays that much further behind and says so beside "shown 30 seconds late"); a server that sends no header has the tag add the usual 10 seconds to the playhead's gap. While the game has nothing to show yet (the match is starting, or shown late and not yet at its first turn) a card over the picture says **Starting…** and, for a match shown late, why and when the picture starts (**The picture starts in 0:22**), and the tag says **starting**; when the playhead has stood at the end of what the game holds for 3.5 seconds with the match not over (a match that is paused, a slow link: the parts come every 2 seconds), the tag says **waiting for the next part · 2 s** (the seconds until the page asks again, none while its look is out) and a note over the picture says **Waiting for the next part…**; **Jump to live** goes to the present, and Download waits until the file is whole. A feed that fails says "The live feed stopped. Trying again…" and goes on trying. When the match ends the door answers 404 with the name of the kept file: the page fetches it, Extends once more and goes on as a replay of the whole match (its address becomes `?replay=<file>`, "The match is over. It is now in the list as a replay."); a match that was not kept ends where the game holds it (`LiveOver`, "The match is over."). A link to a match that has ended has a card with **Watch the replay**, and a link to a match that ended before 30 seconds of play (it is never kept; the door remembers it for 2 minutes) has the card **Too short to keep**, and a link to a match that is not live (or an id that is not the shape of the server's, which is never fetched) says "That match isn’t live". What the door says is shown as text and never as markup. `tests/scripts/test_web_live.sh` (opt-in) checks these pages, and the tag and the fullscreen bar of the player (`--only bar`), in a real browser against a fake door and a stand-in for the game.

**Which files play: `sim_rules`.** A recording plays only on a build that computes the match the same way. That used to be the network protocol's number, which moves whenever the wire format does (v0.12.0 made it 16 for lobby rooms without touching the simulation), so every protocol bump would have stranded the files before it. The head now has its own field, `sim_rules` (a small number, `replay::kSimRules`, 14 now), which changes **only** when a match plays out differently (a golden hash moves: the engine, the map reader, the original's tables). A file plays when its number is one of the numbers of its game mode that the build plays: the original's game, **5** (`replay::kSimRulesBeforeLastSide`, the original's rule of the end alone: a match with one side left and no food played on to the clock), **8** (`replay::kSimRulesBeforeFireWall`, since v0.14: that match ends and the side that is left wins, [`GAMEPLAY.md`](GAMEPLAY.md#the-last-side-standing)) **9** (`replay::kSimRulesBeforeEmptyRecord`, since v0.14: also a fire wall of a map file loads as the original loads it, [`map_loader_fidelity.md`](reverse_engineering/map_loader_fidelity.md) section 8) **13** (`replay::kSimRulesBeforeCantGo`, with the network protocol 25: also a bite takes its unit from the first object of its food tile that has one, so a lunchbox that falls on the anchor of an emptied pile is eaten once, [`GAME_REVERSE_ENGINEERING.md`](GAME_REVERSE_ENGINEERING.md) 5.40, "A lunchbox on the anchor of an emptied record") and **14** (`replay::kSimRules`, with the network protocol 28: also the path manager's answer to a walk that an event asked for is given at the start of the next tick, after the turn's commands, so an ant that an event has just sent takes an order, [`GAME_REVERSE_ENGINEERING.md`](GAME_REVERSE_ENGINEERING.md) 5.40, "The gap before the path manager's answer"); **game mode 187** ([`GAMEPLAY.md`](GAMEPLAY.md)) has **six**: 6 (`replay::kSimRulesMode187Heal`, 187 as first released: the hill works, an ant that enters it is healed, an ant at 1 hp walks home), 7 (`replay::kSimRulesMode187BeforeFireWall`, the hill is closed), 10 (`replay::kSimRulesMode187BeforeEndFix`: also a fire wall of a map file loads as the original's), 11 (`replay::kSimRulesMode187BeforeNoDrops`: also the end rule counts the teams that began, not the seats, and an egg that cannot hatch is no side) 12 (`replay::kSimRulesMode187BeforeCantGo`: also nothing is put on the ground, no power-up from an ant of a special type that dies or that takes another, no lunchbox) and 15 (`replay::kSimRulesMode187`, 187 now: also the path manager's answer to a walk that an event asked for is given after the turn's commands, as 14 has it). The numbers are one row, each of ONE mode, and the next change of either mode takes 16. The loader knows no mode, so its change took one number of each mode (9 and 10), and every number from `replay::kSimRulesFireWallFirst` (9) on has it (`replay::fire_wall_as_original_rules`); the numbers 5 to 8 keep the old loader, which also marks a named fire wall with the remake's obstacle overlay. A build that plays all nine says "5, 6, 7, 8, 9, 10, 11, 12 and 13", records a match of the original's game under 13 and a 187 match under 12, and plays a file of 6 by the old rules (the player sets `SimulationEngine::set_hill_open_187` from the head, so the old recording plays to its recorded hashes byte for byte); a file of 5 is played by the original's end rule alone (the player calls `SimulationEngine::set_last_side_rule(false)` from the head, so a recording that hits the state continues to the clock exactly as it was recorded, and every one that does not is the same match under both numbers), a file of 7 plays the closed hill, a file of 6, 7 or 10 plays without the end-rule fixes (the player calls `SimulationEngine::set_end_fix_187(false)`), a file of 6, 7, 10 or 11 plays with the drops of the original's game (the player calls `SimulationEngine::set_no_drops_187(false)`), a file of 5, 8 or 9 (and 187's 6, 7, 10, 11 and 12, which have no food on the ground) takes every bite from the first object of its food tile as the original does (the player calls `SimulationEngine::set_bite_skips_empty_record(false)`), a file of 5 to 8 loads a map by the old loader (the player calls `SimulationEngine::set_fire_wall_as_original(false)`: the state hash of the 5 library maps whose dictionary names the fire wall `wallup04` differs from tick 0, and in play only a dying ant's power-up drop on a put-out fire wall of the file and the bots' bomb placement there), and a build from before the mode, which plays 1 only, refuses a 187 file for its rules number instead of playing it as the original's game. A mode-0 file never names 6, 7, 10, 11 or 12, and the head check refuses a mode-1 file that names 5, 8, 9 or 13; a number that no build plays (14) is a file and is refused to play, with the numbers this build plays named. The state hash does not carry the rule of 8 (every hash of the original's game is as it was) but it carries the overlay of 9 and 10: the ledger of the 540 maps is the base's under the old loader and differs in exactly those 5 maps under the new one ([`MAP_FORMAT.md`](MAP_FORMAT.md#the-hash-ledger)). A recorder that is given a mode other than 0 stamps the number of that mode whatever the head said. A file made before the field has none: a table in `replay.cpp` maps the protocol numbers that are known to play out the same way (15 and 16 → 1, the number of the rules before the bombs of a map file) and any other number is unknown (0), which no build claims. The server's list says it for every file (`sim_rules`, and the list's own top-level `sim_rules` is the number of the build that serves it), and the page shows the files of another number in a box "Earlier versions", with Download and no Watch. When a change makes matches play out differently, raise `kSimRules` in the same change: `test_replay` RP7.1 - RP7.3 play a reference match and fail when its final hash moves and the number does not (and when the number moves for no reason), so a stranded file cannot slip in; RP7.7 does the same for a reference match of mode 187 and the numbers 4, 6, 7, 10, 11 and 12 (the closed hill moved the hash of 187, so 7 has its own line while 6 keeps the one it had; TINY has no fire wall, no seat without a team and no special ant that dies, so 9 to 12 share the line of 8 and 7), and `test_rules_fire_wall` plays a map made in code with a named fire wall under 8, 9, 7 and 10, `test_rules_end_fix` two matches made in code (a seat without a team, a team of eggs that cannot hatch) under 10, 7, 6 and 11, `test_rules_no_drops` a match made in code in which Combat ants die and other ants take their power-ups, under 11, 10, 7, 6 and 12, and `test_rules_empty_record` a match made in code with two food objects on one tile and six Workers sent to it, under 9, 8, 5 and 13. Raising it adds the old protocol numbers to nothing: the old files stay in the list under "Earlier versions" until their days are over (90 in the stack). One change did not move the number: since v0.12.97 an order to exactly column 120, row 90 on a map of **rules 1 or 2** (a new Extended map of more than 90 rows or more than 256 columns) is a real target, where it used to read as "no order" (the old marker was that tile); a recording of such a map with such an order, made before, may not play out the same. No library map, no Classic map and no Extended map of rules 0 is affected (their play and their hashes are exactly the ones they had, [`MAP_FORMAT.md`](MAP_FORMAT.md) "Rules"), so the number and the protocol number stay. Since v0.14 a map can also carry the **rules word 2** (the wide search of the path finder, [`MAP_FORMAT.md`](MAP_FORMAT.md) "Orders on a big map"); that did not move the number either: the word is part of the map, which the recording names by its hash (and carries when it embeds it), nothing before it used the word, and a build that does not know it refuses the map, so it never plays such a file by other rules; a match on such a map plays to the same hashes under every number that a build plays, 5 to 11 (`test_rules_two`). One more case, from the same release and mended in v0.12.104: on a map of **rules 0** with 91 or more rows and 121 or more columns (none exists in the library or in what the tools make; only a hand-made file) the hash of v0.12.97 to v0.12.103 had an extra byte for as long as an ant held the tile (120, 90), which v0.12.93 and v0.12.104 do not have, so a recording of such a map made by v0.12.97 to v0.12.103 fails verification at the first 100-turn checkpoint that falls while an ant holds that tile (it is chance whether one does), and a live game between those builds and v0.12.104 reports a desync at the first 20-turn check inside such a time. And one more that did not move it: since protocol 22 the layer-2 id 38 (`bridge4b`) is no bridge, as in the original ([`GAME_REVERSE_ENGINEERING.md`](GAME_REVERSE_ENGINEERING.md) 5.37); no map of the library holds it (the hash ledger of the 540 maps is byte for byte the one it was, and the reference match of RP7.3 ends where it did), so only a recording of a player's own map that holds the id, made before, may play out differently, and the rules number stays 5.

## A file of your own

A visitor who has a `.antsrep` (downloaded from the site's list, or from the desktop game's `replays` folder, or saved by `bot_arena --save-replays`) can watch it on the site. The **Matches** page has a strip **Got a replay file?** above its tools, always there (also when the list is empty): a button **Open a replay file** (full width on a phone) and, on a computer, a drop of a file anywhere on the page (a veil says "Drop the replay file to watch it" while a file is dragged over; a drag of text or a link is none of the page's business). **Nothing is uploaded.** The page reads the file on the device, leaves it in the browser's own storage and goes to the player in the same tab: `/play?local=<id>`.

- **What is asked before the game is loaded** (`localCheck` in `web/replay_page.js`; the game, 15 MB, is not fetched for a file that fails): the size from `File.size` before one byte is read (at most 17,825,804 bytes: `replay::kMaxFileBytesWithMap`, a match and the map it may carry) and again on the bytes, the 8 bytes that open every replay (a transfer that changed the line ends is noticed), a `HEAD` chunk right after them, at most 4096 bytes long, with the right checksum. The chooser has **no `accept` filter** (a phone's chooser greys out a file of an ending it does not know), so the bytes decide, not the name. A file that fails shows a card under the strip, in the approved words (**That file is too big**, **That file is not a readable replay**, or, for a browser that keeps no site data, **This browser will not keep the file for the player**) and nothing else happens; the record that was there stays. The rules number, the map and every other chunk are the game's to judge, as for a recording of the server: the cards **Recorded by an older version** and **Recorded by a newer version** come after the game has loaded, and the page does not guess them.
- **The hand-off** (`ownStore` in `web/replay_page.js`): one record in IndexedDB (`ants-own-replay`, the store `slot`), under a random id of 32 hex digits; a second file takes its place. The player reads it by the id of its address, so a reload works (the record stays); a record older than a day is thrown away by either page when it opens (a clock put back by more than a minute does not keep one for ever). An address with no record (an old link, another tab took the place, the browser's data was cleared) is the card **Choose the replay file again**, with a chooser, and the game is not started; a browser with no IndexedDB says so on the Matches page. A file that does not pass is never written: the record that was there stays.
- **The player** is the game page in its replay mode (`ANTS_OWN_MODE` in `web/shell.html`, the body class `ownfile`; `replay=` wins over `local=`, which wins over `live=`). Its header says the map, **Your file**, the name of the file and the length of the match, and the players (what the game reports, until then what the head of the file says); there is no date (the desktop game names a file with the local time and no `Z`, so the time cannot be read from it). The buttons are **‹ Matches** and **Fullscreen** (on a phone **More** holds **Open another file**); there is no **Copy link**, **Stats** (the server's record of its own match) or **Download** (the file is already on the device), and every card that could offer the file for download offers **Open another file** instead. The words of these cards are in `ownPage` (`web/replay_page.js`), so `web/shell.html` only calls them.
- **Maps.** The six originals are in the game's data. A map of the library or an approved community map is fetched from `/maps/files/<name>` by the name in the head and checked against the head's hash, as for a recording of the server (the site learns the map's name and nothing else; a name that the game would not take is never asked for, and the address is percent-encoded). A file with a `tmap` chunk carries its map: it is checked against the head's hash and used with nothing fetched. A recording that the desktop game made on a map of its own, or on a Map Maker test map, carries no map: the card **This site doesn’t have the map** (the map's name, "a replay needs the same map file", and the way out); the same card says the site has a map of that name that is another file when the hash differs.
- **A damaged or made-up file.** Everything a file says (its name, the map, the players) is put in as text, never as markup; the chips show the names the game reports; the size is held twice here and once more by the game's reader (`replay::decode`, which refuses a file before it reads a byte); a file of at most 17 MiB (a match of 16 MiB and the map of 1 MiB that it may carry) is the most the page holds. A file that claims 2^21 turns makes a jump in its own tab slow, and the page goes on answering. What could hold the tab's one thread for much longer is setting up the match, and a map that the file carries can make that long in two ways, each a SQUARE: the ants (set up in a time that grows with the square of their number: natively about 50 ms for 6,000, 9 s for 40,000, and more in a browser, where no timer can run meanwhile) and the plants times the waypoints (for every plant that drops flowers the engine scans the waypoints from the first for the one on its cell, so 65,400 plants and 65,535 waypoints, 4.3 billion pairs, take seconds natively and a minute on a phone; the largest map of the library has 112 plants and 114 waypoints). So a map that the file carries is counted before the game starts (`factsOfMap` in `web/map_files.js`: the start markers, the plants and the waypoints, as the loader and the engine count them) and a map that starts more than 8,000 ants (`kMaxEmbeddedStartAnts`) or has more than 1,000,000 pairs of a plant and a waypoint (`kMaxEmbeddedPlantWaypointPairs`; the largest map of the library has 12,768) is refused with a card that says the numbers; 8,000 is above every map of the library (at most 248) and of the players (at most 6,000). The game counts the same (`fits_a_replay` in `src/ants_replay/player.cpp`) for the map that the file carries WHICHEVER copy it reads, the file's own or the copy that the page writes into the maps folder under its name (that copy is the one it reads on the web); so for the web page the page's count is the first guard and the game's the second, and a page that does not count (an older one) still gets the game's refusal. A library map that the file does not carry is the site's own file and is not counted. A map that the file carries (at most 1 MiB) is read by the game's own map reader inside the WebAssembly sandbox, after the hash check; `tests/scripts/web_replay_open_fuzz.sh` runs the native decoder and map reader on mutated copies of such a file. A map that the game itself refuses (its rules word, its format flags, markers outside its grid, a grid beyond the limits) gets the game's own reason in the card, never the words for a map that the site does not have.
- **Tests.** `tests/scripts/test_web_replay_open.py` (its header lists them) runs `web_replay_open_check.js` (the checks above on `tests/data/replay_bots_tiny.antsrep`, a real 3 KB recording from `bot_arena --save-replays`, on every cut and flipped bit of its head, with a fake IndexedDB and a fake page) and the list of mutants `tests/data/replay_open_mutants.json` (95, run by `tools/mutate.py` and, on a copy of the files, by the quick tier); the limits on the ants and on the plants times the waypoints of a carried map are tested natively (`RP9.11` and `RP9.12` of `tests/test_replay`, `RA7.10` to `RA7.13` of `tests/test_app/test_replay_app.cpp`: the limits at their edge, the largest file (65,400 plants and 65,535 waypoints), the maps folder's copy, all 540 maps of the library; `RP9.12`: the recording of `tests/data` plays to its last hash, so a change of the simulation that strands it fails there; `S3.231b` of `tests/test_server` pins the viewer's limit on ants at least the rooms' cap; 17 mutants in `tests/data/replay_ants_guard_mutants.json`); the opt-in `tests/scripts/test_web_replay_open.sh` is a real browser against a stand-in for the game (the bytes the game gets are the file's, no request has a body, a reload, a record that is gone or too old, every card, the Matches page with the site down, a phone with a file name of 100 characters, a map name of 59 and player names of 64, a file name that reads right to left) and draws the pictures with `--shots DIR`; given a running site (`ANTS_WEB_URL`: the web image, or `python3 tools/web_without_docker.py`) it also runs the real game: it plays the file and the jump on its timeline, says an older or newer version, reads a map that the file carries, refuses a crowd of 65,535 ants and 65,400 plants with 65,535 waypoints in no time (the page, the game under the name of an original, and the game alone when the page does not count), gives the game's own reason for a map that it refuses, and meets nine damaged maps. CI does not run it (it runs no browser).

## Matches of computer players

`bot_arena --save-replays DIR` (the tool of [`BOTS.md`](BOTS.md)) keeps every match that it plays as a replay of the server's kind in the folder `DIR`: the names `ants-<MAP>-<date>-<time>Z.antsrep` (the UTC time of the write, a `-2`, `-3` ... when the name is taken), written whole under a temporary name and renamed, and a file that is there is never replaced. The head says venue "bot arena", no Fog of War and the display names of the bots ("Bot (Medium)", "Bot (Hard)"), so the list shows them as "Green (Bot (Hard))" like the bots of a room, and the player plays them back to the hash of the arena's own match (the tool's self-test checks this). A match under 30 seconds is not saved, as on the server. **How they reach the site's list:** point `DIR` at the server's replays folder (`replays` in its results volume). The arena deletes nothing and has no limits of its own, so pointing it at the server's folder does not cost the server a file. The server looks at that folder again every 30 seconds when its change time moved (`ReplayStore::rescan`): a file that was put there is listed (one that changed in the last two seconds waits for the next look, so a copy that is still growing is not taken for a damaged file; a file that could not be read or changed its size is read again), a file that was taken away is forgotten without deleting anything, and the server's own limits then apply to the files from outside too: a file older than the kept days that is copied in is deleted again at once. A store that opens the folder deletes the half-written `.tmp` files of a crash, but not one that changed in the last two seconds (`settle_s`): that is the write of the other program, which renames it in a moment, so the server and the arena can open the folder at any time. Two writers of the same name in the same second could still replace each other's file (a rename replaces on Linux), and never run two arenas on one folder at the same time.

The game server plays matches of computer players of its own too (by a schedule or from the admin page, [`SERVER_REPLAYS.md`](SERVER_REPLAYS.md#matches-of-computer-players)): a room with no person in it, free for all or in teams (the head of the file holds them, as for any match), at the normal speed, recorded and listed like any room's match, and shown in the list of the matches that are being played while it goes on. Those matches are what the "Live now" box of the list shows when nobody else is playing. The stack runs no other program that plays bots: `bot_arena` is run by hand.

## The file

A `.antsrep` file is a row of chunks, like a PNG: a reader skips a chunk that it does not know (unless its first letter is upper case: then the file is refused), every chunk has a checksum, and a file that stopped in the middle still plays up to its last whole chunk. The numbers are little endian. [`include/ants_replay/replay.hpp`](../include/ants_replay/replay.hpp) has the exact layout; in words:

| Chunk | Holds |
|---|---|
| `HEAD` | the format number; the protocol number (information); the simulation rules number `sim_rules` (what a build plays a file on, "Watching a replay"); the game's version and build; "local game" or "network game"; the map's file name and its hash; the seed; the seats that play; Fog of War; the names; the teams that the match started with; the game mode (head field 17, one byte, **written only when it is not the original's game**: a file of the original's game has no such field and is byte for byte what it was before the modes); the seat of the machine that wrote the file; the seats whose orders went over their budget (head field 18, one byte with a bit for each seat, **written only when a seat has it**: the "heavy order rate" mark, [`NETWORK_PORT.md`](NETWORK_PORT.md), "The order budget"; the orders beyond the budget were not sealed, so they are in no file, and nothing plays differently; `replay_tool info` names the seats) |
| `CMDS` | the orders in the order in which the engine was given them, each with its turn; one chunk for every 30 seconds of game time or 4,096 orders |
| `hash` | the low half of the engine's state hash after every 100th turn (every 5 seconds of play) |
| `tmap` | optional (its tag is lower case, so a reader that does not know it skips it, and the format number stays 1): the bytes of the map file, exactly, for a match on a map that the server keeps only for a while (a test map). It stands right after `HEAD`, so a copy that was cut short still has it. **At most one**, at most 1 MiB, and the FNV-1a 64 of its bytes must be the `HEAD`'s map hash: a file with two, with one over the cap (refused from its length, before any byte of it is looked at), an empty one, or one of another hash is refused with the chunk named. A map that starts more than 8,000 ants (`kMaxEmbeddedStartAnts`: the start markers of the four colors added up) or has more than 1,000,000 pairs of a plant and a waypoint (`kMaxEmbeddedPlantWaypointPairs`) is read and then refused (`fits_a_replay`, asked by `load_embedded_map` and by `load_map_or_embedded` for the folder's copy of such a map), because setting such a match up would hold a viewer's machine for seconds to minutes ("A file of your own"); a writer keeps to both. Never in a snapshot (`live`): a live view still fetches the map by its name. A file without it is byte for byte what it always was (`tests/test_replay`, RP9.2). Nothing writes it yet in a game (the server's change that records test games is the next one); the readers do |
| `ENDS` | the number of turns, whether the rules ended the match, and the state hash at the end. A file without it is incomplete: a copy that was cut short (a download that stopped, a file that was truncated), because the game writes a file whole, when the match is over or left, or a snapshot of a match that still runs (`live`, below) |
| `live` | only in a snapshot of a match that still runs ("On the game server"): the number of turns the match had run when the snapshot was made, which can be more than the last order and the last hash say. It is optional and its tag is lower case, so a reader that does not know it skips it. A reader that does takes the file's length from the largest of its last order, its last hash and this number, and refuses a file that has two of them, one of the wrong length, one with fewer turns than its last order or hash, or one together with an `ENDS` chunk |

An order is the network's own wire form (the one a room sends, [`NETWORK_PORT.md`](NETWORK_PORT.md)): its type, who gave it, the tile, the ants that it names by number. **Turn t** is the t-th tick of the engine: the orders of turn t are given first, in the order they stand, and then the tick runs (a turn is 50 ms). Orders at the last turn's number come after the last tick: a Quit that ends the match is one.

**The rules number** that a file is played on is `sim_rules` ("Watching a replay"; `replay_tool info` shows it with the protocol number that the room spoke). A file is played only by a build that plays its `sim_rules` (the original's game 5 (the original's end rule alone), 8 (the last side standing), 9 (the fire wall of a map file loaded as the original's), 13 (a bite takes its unit from the first object of its food tile that has one) and 14 (the path manager's answer to a walk that an event asked for is given after the turn's commands), game mode 187 the numbers 6 (the hill works), 7 (the hill is closed), 10 (the same, with the fire wall loaded as the original's), 11 (the same, with the end-rule fixes), 12 (the same, with nothing put on the ground) and 15 (the same, with the path manager's answer to a walk that an event asked for given after the turn's commands); the numbers 3 and 4 were theirs from the bombs of a map file, v0.12.9, to the loader as the original's, v0.12.10, and 1 and 2 before); another build still reads its header, and the message names both numbers and the game that made the file. **The mode and the number go together**: a head with a mode that is not 0 names the rules number of that mode, and a head that names the rules of mode 187 (6, 7, 10, 11, 12 or 15) names the mode, a head that names the rules of the original's game (5, 8, 9, 13 or 14) names no other mode, so a file with one and not the other (or a mode this build does not know) is no file (the writer refuses to make it and the reader refuses it, with the field named). The recorder takes the mode from the match's Start (the server's referee, the network game's Start, the local game's engine), and the player makes its engine with it before the first tick. The list of the server and the tool say the mode (`"mode": "187"`, `replay_tool info`: "game mode 187"), and a mode-0 file shows no difference. (Before the field, the network protocol's number stood for it, and a file without the field is read through the table of protocol numbers that are known to play out the same way.) **The map** is found by its file name in the folder of the shipped maps (`--maps-dir` names another) and must be the same file: another file under that name is refused with both hashes. **A file that carries its map** (`tmap`) uses the folder's map when the folder holds that file, and its own map when the folder lacks that name or holds another file of that name; its own is loaded as any map is (the head's hash, then the limits of playing a map), and nothing is ever written into a folder. On the web the page fetches a map of the players from the site before the game starts ([PLAY_MATCH_SETUP.md](PLAY_MATCH_SETUP.md#players-maps-in-the-browser)), unless the file carries its map: then the page checks its bytes against the head's hash and gives them to the game, and fetches nothing.

**Size:** a match of computer players is a few KB (4 KB for two and a half minutes of four of them on the smallest map), a long match of people tens of KB. A click on a big selection (more than 32 ants) is several commands and adds to that: a move of 693 ants (22 commands) about 2.9 KB, a Stop of 1,500 ants about 6 KB. A recording whose MATCH would pass 16 MiB is not kept (a game on a computer says so on its console; a server's room, when the match ran 30 seconds or more, in its `replay.note` and in the log): `kMaxFileBytes` is the size of the file without its `tmap` chunk, so a file that carries a map may be that much longer than the map's chunk, and the longest file there can be is 17 MiB and the 12 bytes of the map chunk's frame (`kMaxFileBytesWithMap`; a reader refuses a longer one before it reads a byte). A build from before the `tmap` chunk refuses a file of more than 1 MiB whatever it holds, so a file with a big map does not open there (nor does a match of more than 1 MiB on a build from before the limit was 16 MiB); the game server's public door sends a replay as a file (`HttpResponse::file`), which it needs for anything over 1 MiB (`tests/scripts/test_nginx_big_replays.py` sends 1.5 MiB through the real server and the real nginx blocks).

## The tool

```bash
cmake --build build --target replay_tool
./build/replay_tool info    match.antsrep      # what the file says: map, seed, seats, teams, length, orders (no map needed)
./build/replay_tool verify  match.antsrep      # plays it and compares every hash in the file and the final state
./build/replay_tool orders  match.antsrep      # plays it and lists every order
./build/replay_tool orders  match.antsrep --seat 1 --type bomber     # only the orders of Red that name a bomber
./build/replay_tool orders  match.antsrep --csv > orders.csv         # a table for a spreadsheet
./build/replay_tool map     match.antsrep draft.lvl              # the map that the file carries, to a NEW file
```

(`build\replay_tool.exe` on Windows.) `--seat N` is 0 Green, 1 Red, 2 Blue, 3 Black; `--type` is worker, bomber, fire, thief, combat or swimmer; `--maps-dir DIR` says where the maps are (a map that is not there, or another file of that name, is the file's own map when the file carries one; `info` says "embedded map: N bytes" then). `map FILE OUT` writes the map that the file carries to the new file `OUT` and nothing else: it refuses a file that carries none (exit 1), a path in the map library (`Original-Ants`, `Community-Maps`: no tool writes there), the file it reads and a file that exists already (exit 2). The exit status is 0 when the file was read (and, for `verify` and `orders`, played to the end with every hash right), 1 when the file is refused, its map is missing or the match does not play out the same here, and 2 for a wrong command line or a file that cannot be read. A file that stops early plays as far as it goes and says so; if it holds no hash either, `verify` has nothing to compare the match with and says UNVERIFIED (exit 1) instead of OK.

`orders` prints one line for each order:

```text
TINY.LVL, seed 5: Green, Red, Blue, Black; 3000 turns (2:30.0)
  time  turn  seat   order  place    ants      from     result
0:00.6    12  Green  move   (12,12)  3 Worker  (9,8)    ok
0:00.7    14  Red    move   (18,18)  3 Worker  (21,21)  ok
...
291 orders: Green 57, Red 92, Blue 65, Black 77
```

- **time** is the game time of the order (minutes:seconds.tenths since the first tick), **turn** the turn number, **seat** the color, with the name when the seat has one ("Red (Bot (Hard))").
- **order** is `move`, `special`, `attack`, `stop`, `hatch`, `team offer` / `accept` / `refuse` / `withdraw` / `leave`, `quit` or `dropped out`; **place** the tile of a move, special or attack, or the other side of a team order.
- **ants** are the ants that the order names, by type ("3 Bomber, 1 Worker"), read off the engine as it stood when the order was given: an order names its ants by number, and only the engine knows what an ant is. Ants that were gone, never were, or belong to another seat are counted as "not there" (the engine leaves them out). **from** is the tile where the first of those ants stood.
- **result** is what the engine said: `ok`, `ignored` (nothing for it to do, for example every ant named was gone) or `refused`.

With `--csv` the same lines come as a table (`time,turn,seat,name,order,x,y,ants,from_x,from_y,result`; the text cells are in quotes). A text that begins with `=`, `+`, `-` or `@` (a name in someone else's file could) gets a `'` in front, so that a spreadsheet shows it as text and never takes it for a formula.

A **special** order is what the ant's type does with it ([`CONTROLS.md`](CONTROLS.md#mouse-controls), [`GAMEPLAY.md`](GAMEPLAY.md#special-abilities)): a Bomber plants a bomb at the place or defuses one, a Fire ant lights a fire wall or puts out a blaze, a Swimmer digs a bridge on water or demolishes one, a Thief raids a hill. For a group of workers, combat ants or mixed ants it is a plain move. After the table the tool counts the special orders by the type of ant that got them: "special orders by ant type: Bomber 12, Swimmer 3" is how to see at once whether a player bombed with bombers and dug bridges with swimmers.
