# Workflow: light checks, deploy, base images and browser checks without Docker

Part of [Workflow](../WORKFLOW.md): the sections about the site's deploy, its images and the checks that read them. The tiers, branches, releases and the version policy are in that page.

## Light checks for web and document pull requests

For a **pull request** (never a push to `main`, never a manual run) whose changed files are **all** of the light kinds, CI skips the macOS and Windows legs; Linux (all its jobs) and the web legs run as always. The first job of the run, "Which checks does this change need?", decides with `tools/ci_light.sh` (plain shell and `git diff` against the merge base of the pull request and ITS OWN base branch, whatever that is (but a pull request into `main` is always full, whatever it changes); the workflow runs again when a pull request is edited (`edited`: a new base branch is one of the edits, and so are a new title or text, which cost one more run), so the decision is made for the base the pull request has now; a renamed file counts under both names, a deleted one counts, a bumped submodule counts; the decision and every changed file are in the log; tested by `tests/scripts/test_ci_light.py`):

| Light | Full: anything else, among it |
|---|---|
| `web/`, `docs/`, `CHANGELOG.md`, `README.md`, `tests/data/*_mutants.json`, and the page tests `tests/scripts/test_web_*` and `tests/scripts/web_*` (files of that folder only, not in a folder below it), except the files named under "What the skipped jobs read" | `VERSION` (a change that goes live is never light), `CMakeLists.txt`, `cmake/`, `src/`, `include/`, `tools/`, `hub/`, the Dockerfiles and compose files, `.github/`, `third_party/`, `Community-Maps/`, `Original-Ants/`, `run_tests.*`, the C++ tests, the other tests and helpers of `tests/scripts` (macOS runs most of them and the two shell suites), the other files of `tests/data`, the files named below, and every path that is not listed |

Unknown is full. So are a pull request into `main` (the full checks are the gate of `main`), a pull request whose base branch is not named in plain characters, a pull request with no changed file, a history without a merge base with its base, a git that fails, and a first job that fails (the five checks then fail, and the legs of macOS and Windows do not run). The job reads the commit ids of the event and the name of the base branch and nothing else of it (no title, head branch name or body reaches a script; the base name is compared with a literal and a list of plain characters, never evaluated and never printed by the script), and its permissions stay `contents: read`.

**What the skipped jobs read.** macOS and the two Windows jobs build the game and run the C++ tests (ctest, on all three systems), the tool self-tests, the E2E runner and, on macOS, the two script suites. None of these reads a light file, because the few that they read are full: ctest needs the six pictures of the original maps (`web/front/preview_*.png`); the server script of the macOS job (`tests/scripts/test_ants_server.sh`) reads the two pages (`web/lobby.html`, `web/shell.html`) and the rules of the lobby page (`web/front/lobby_rules.js`) and runs the lobby page against the real server and the native game in the fake browser of `tests/scripts/web_page_harness.js`, with `web/shapes.js`, `web/rejoin_key.js` and the scripts of the page that the harness loads (`web/front/lobby_net.js`, `player_name.js`, `lobby_chat.js`, `rematch.js`, `game_modes.js`, `game_type.js`, `map_picker.js`, `web/home/home.js`, `web/home/games.js`), by the node checks `web_fill_check.js`, `web_lobby_server_check.js` and `web_lobby_handoff_check.js`. So a change to the lobby page is full; a change to the Map Maker, the admin page, the history, replay and match pages, Home's chat, a document or a page test is light. `tests/scripts/test_ci_light.py` finds the C++ and the scripts that name a file of `web/` or `docs/` and fails when the list is not whole.

**What a light pull request does not get.** macOS also runs most of the python tests (all but the `LINUX_ONLY` groups), and these read pages and documents: the repository checks read every document, `CHANGELOG.md`, `README.md` and the lists of mutants, and the page tests read the pages. Linux runs every one of the same tests in every run, light ones too, so a light pull request is checked by them; what it does not get is their second run on macOS, which could show a difference between the systems only (another version of node, say), and nothing runs them on macOS until the next full run (a pull request into `main`, a push to `main`; a light pull request into `home-next` is not followed by a run there). What a checkout there shows and Linux does not, a name that Windows or macOS cannot hold (two names that differ only in case, a reserved or forbidden name, a path that is too long), is refused on Linux for every pull request, light ones too: `tools/check_portable_paths.py`, run by `tests/scripts/test_portable_paths.py` among the python tests.

What is skipped: the legs of macOS (two) and of Windows (one matrix of four legs: two for each compiler) are *Skipped*, which GitHub counts as passing for a required check. A matrix job that a job-level `if` skips is reported once under the unexpanded template of its name, so the five required names are carried by small jobs that always run (`linux`, `macos`, `windows_2022`, `windows_2026`, `web` in `ci.yml`): each runs in a second, passes when its legs passed, and for macOS and Windows also when the first job succeeded, said `true`, and the legs were skipped. A failed, cancelled or skipped first job passes none of the five names; tests/scripts/test_ci_workflow.py runs every small job in bash against every combination of results. The Windows legs are one matrix, so a failed leg of either compiler turns both Windows names red.

**The five names belong to a commit, not to a base.** A commit that was checked as a light pull request into `home-next` keeps its five green names when the same commit is offered to `main` (the base is changed, or a second pull request is opened from the branch), until the run that starts then has its small jobs report. A small job exists as a check only when the jobs behind it have ended, so the old names stand for the length of the new run (22 to 47 minutes were seen when the runner pool was full). What the workflow does about it: a pull request into `main` is always full, so the new run is a full one; the run starts at once when the base is changed (`edited`); and the runs of two pull requests of one branch do not cancel each other (the concurrency group is the pull request number), so the survivor is never the one judged against the other base. While two pull requests of one branch are open (one into `home-next`, one into `main`), this window comes back at every push, not only when the second one is opened: each push starts both runs, the light run's macOS and Windows names are green within a minute or two, and the full run's appear only when its legs end, so for some minutes the commit has five green names, two of them from the light run. Auto-merge on the pull request into `main` would not wait for the new run in that time, so it must not be turned on for a pull request into `main` whose commit also runs against another base. What stays, and is a rule for whoever merges: **a commit that was checked against another base is not merged into `main` on those results; wait for the run that the change of base started (all five names new), or push a new commit.** The release procedure makes a new commit on its own branch (the `VERSION` change), whose head has never had a run against another base. Linux and the web legs run in full for every commit in every case; what a light run lacks is macOS and the two Windows compilers.

If the first job fails on a push to `main`, the macOS and Windows legs do not run and the run is red: re-run it.

**What makes a run faster, and what does not.** The python tests run in three slices (`run_python_tests.py --shard K/3`), and the two long mutation classes, `test_web_home_games.TheChecksAreNotVacuous` and `test_web_home_chat.TheChecksAreNotVacuous`, are four units each (`NAME[K/4]`: unit K tries the mutants at the positions K, K+4, K+8, ... of the same list, through `tests/scripts/mutant_shard.py` and the variable `ANTS_MUTANT_SHARD`): the same mutants and assertions, each mutant tried once (`test_run_python_tests.py` checks that the units together are the whole list), and a plain `python3 -m unittest` of the class tries all of them. The web checks are two legs side by side (the web image and its checks; the server and hub images and the stack files). Docker layers are cached in a folder (`docker buildx build --cache-from/--cache-to type=local`, kept by `actions/cache`, keyed by a hash of the files that the compile layers read: the Dockerfile, `.dockerignore`, `docker/emsdk_warm.cpp` (the web image only), `CMakeLists.txt`, `cmake/`, `include/`, `src/` and, for the server image, `third_party/`): the image is the same, and a change that leaves those files alone (documents, tests, hub, nginx, compose, and also `web/`, `VERSION`, `web/shell.html` and `Original-Ants/`, which the Dockerfile copies after the compile, and `tools/`, which the server image does not copy) reuses the compiled game. A change to `src/`, `include/`, `cmake/`, `CMakeLists.txt` or a Dockerfile makes a new key and recompiles. If the Dockerfile copies another file before the compile, or moves a copy across the compile, the key of the leg (`ci.yml`), its test in `tests/scripts/test_ci_workflow.py` and this sentence change with it. The `--mount=type=cache` folders of the Dockerfiles (ccache) live in the builder and are not exported with the layer cache, so they are empty in every run of CI: when a compile layer is rebuilt (a change of C++ or of the build files) CI compiles every file, where the host that builds the stack compiles only the files that changed. The time saved in CI comes from the layer cache alone. A new key costs about 0.9 GB of the 10 GB that GitHub keeps for the repository (the least recently used entries go first; `home-next` has no push run, so a pull request reads only `main`'s caches and its own, and the gain is mostly from its second run on). A cached layer does not run its commands again (an `apt-get` of `Dockerfile.server`, the Emscripten ports fetched in the web compile), so a break upstream shows when the layer is rebuilt, not before. The builder is `moby/buildkit` at a pinned release.

## Deploy

CI does not deploy. The production site syncs from `main` through the host's own automatic update of the stack (`docker-compose.stack.yml`); a merged pull request is live when that update next runs. Nothing in CI waits for the checks of `main` or for a quiet game server, and the update recreates the game server's container, which pauses the matches that run: the server writes a restart record for each and the players come back to the same match when it starts again (docs/NETWORK_PORT.md, "Restart records"); the site gives no promise of uptime. Every image of the page and of the game server carries the build id of the commit, so each commit recreates them; the chat hub is recreated only when its own files changed ([`HUB.md`](../HUB.md), "Deploys").

*What starts the update is the operator's, and it acts on `main` only.* The host's own automatic update, or a webhook that the repository sends on a push if one is set up, starts the update of the stack. The side that receives it must ignore a push to any branch but `main` (agents and people push many branches, and none of them is a release) and must not update while a match runs (AGENTS.md, rule 1). The repository holds no address or secret of such a receiver; "Switching to a webhook later" below says how CI could send the call instead, for `main` only.

*After the first release with these Dockerfiles.* The images are built by BuildKit (the default from Docker 23; [`BUILD_AND_RUN.md`](../BUILD_AND_RUN.md), "BuildKit is required"). If the build id in the last line of the front page's Menu (the same line ends the Menu of the other pages with a bar, the game page's included) does not change after a release, the build failed on the host and the old version keeps serving: read the build log of the stack. Run `docker system df` before the release and again after a good one, and `docker builder prune` once the release is live and good: the layer cache and the compiler cache grow with every C++ release until then. The first build on the host reuses no layer and takes ten minutes or more; later builds that change only pages or `VERSION` take a few minutes.

*Switching to a webhook later.* To let CI start the update, turn the host's automatic update off, keep the stack's webhook address as a repository secret, and add a last job to `ci.yml` that needs every other job, runs for a push to `main` only, and sends one POST to the address (read from the environment, never printed and never put on a command line). A wait for a quiet server can poll the site's public `GET /busy` ([`NETWORK_PORT.md`](../NETWORK_PORT.md)) before the call. Each piece needs its own tests, and `tests/scripts/test_ci_workflow.py` currently asserts that the workflow has no deploy job and no secret.

## Dependencies and base images

The base image of every Dockerfile is pinned by tag and digest (`name:tag@sha256:...`: the digest is what is pulled), the image converter's package by version and by the hash of its files (`imgconv/requirements.txt`, installed with `--require-hashes`), and the actions of the workflow by their major version. `.github/dependabot.yml` has Dependabot propose, once a week and against `home-next`, one pull request for each of the three kinds; CI builds the images in it like in any other pull request, and a person merges it. A new minor or major version of the Python interpreter or of Emscripten is not proposed: it changes what the images compile and run, and is taken on purpose. A security update comes from the repository's setting for them, for the default branch, and is brought into `home-next` by a pull request of its own. `tests/scripts/test_supply_chain.py` keeps the pins and the file.

## Browser checks without Docker

The opt-in browser checks that need only the page (`test_web_aspect.sh`, `test_web_edge.sh`, `test_web_touch.sh`, `test_web_home.sh`, `test_web_camera.sh`, `test_web_changelog.sh`, `test_web_replay_lock.sh` and `test_web_replay_map.sh`, which also need a recording: its header says how to make one) need a running copy of the web image, and a session that has no Docker daemon (a cloud session) cannot build one. `tools/web_without_docker.py` makes the same pages without it and runs a command against them:

```text
sudo apt-get update && sudo apt-get install -y nginx                    # once
tools/web_without_docker.py -- tests/scripts/test_web_aspect.sh          # build, serve on 127.0.0.1:19980, run, stop
tools/web_without_docker.py --context ../other-worktree -- tests/scripts/test_web_home.sh
```

It replays the Dockerfile on the machine (`FROM`, `ARG`, `ENV`, `WORKDIR`, `COPY` with `.dockerignore` and `--from`, `RUN`; `/src`, `/usr/share/nginx/html`, `/etc/nginx` and `/srv/community-maps` live under `scratch/web_without_docker/fs`), so the pages are stamped and checked by the Dockerfile's own commands. Emscripten (the version of the `FROM` line) is installed with emsdk the first time (a few minutes, kept in `.cache/ants-web` of the home folder; a run that is cut short is finished by the next one), and its ports (SDL2, SDL2_ttf, FreeType, HarfBuzz) come from git tags and Emscripten's own mirror, because such a session may not download GitHub archives (github.com and storage.googleapis.com must be reachable). nginx serves the files with the real `docker/nginx.conf`. The command gets `ANTS_WEB_URL`, and `CHROME` when it is not set: a script that starts Playwright's headless shell (Chromium's new headless mode stops giving a page the mouse once the page has left fullscreen, which fails the aspect check), else Chromium, with the mouse of a desktop (a headless browser on a machine with no mouse has no pointer that hovers, and the page hides what is for a mouse) and, as root, `--no-sandbox`. `--reuse` serves the last build, `--keep` leaves nginx running, `--build-arg` takes the Dockerfile's `ANTS_BUILD_ID`.

It does not replace CI's `docker build`, which stays the gate for the image (the runner stage, `nginx -t`, the image checks), and it is no use on macOS or Windows (use Docker there). It starts no game server, but nginx answers `/maps/all` (the list of the game's map names, which the Map Maker asks for when it starts) at once from the maps of the image, so that no name is looked up and no resolver waits (the other routes of the game server answer 404 after a second); `test_web_home.sh` leaves out its parts that play, and `test_web_hidden.sh`, `test_web_prediction.sh` and `test_web_rejoin.sh` say SKIP and exit 0 without one, which is no pass. The ports are not the archives that Emscripten checks by hash, so a change of the Dockerfile or of an Emscripten port still needs the real build. A `RUN --mount=type=cache` is played without the mount (this tool has no cache, and the Dockerfile's `ENV CCACHE_DIR` becomes a folder of the scratch space, so that the replay never trims or fills the machine's own compiler cache), the stage `emsdk-warm` (system packages, Emscripten's libraries and ports, which the tool installs itself) is not played, and a Dockerfile instruction that it does not know (`ADD`, `ONBUILD`, any other `RUN` flag, ...) is an error, never a step that is left out. Its tests: `tests/scripts/test_web_without_docker.py`.

## The image check

The sixth job of the CI table (`docs/TESTING.md`), "Image files unchanged by a Dockerfile change", is not one of the checks that `main` requires: for a pull request that changes a Dockerfile it builds the images from the base and from this tree and compares what the final images hold and what the link reads (`tools/image_files_diff.sh`). A pull request that adds a `COPY` line (a new page file) or an input of the link changes the images on purpose, and the job reports that as a note and passes (what is still red, and the rest of the rule, is in [`BUILD_AND_RUN_DOCKER.md`](BUILD_AND_RUN_DOCKER.md)). It stands behind none of the five names (not behind "Web (Emscripten, Docker image)" either): a name can say "skipped is fine" only for all the jobs behind it together, and whether a change of the images was meant is for the person who merges to say. It runs when a Dockerfile, `docker/emsdk_warm.cpp` or one of the check's own tools changes.

**The image check is read by the person who merges.** The job "Image files unchanged by a Dockerfile change" is not one of the five required checks, and a red one blocks nothing by itself. Whoever merges a pull request that changes a Dockerfile, `docker/emsdk_warm.cpp` or the check's own tools (`tools/image_files_diff.sh`, `tools/image_manifest.py`, `tools/link_inputs.py`, `tools/relink_outputs.sh`) reads that job's log first, and does not merge on red unless every difference it lists is an intended one that the pull request text names. A release pull request into `main` that carries new `COPY` lines shows exactly those files as notes ("added by a COPY line of the change"): for the release that adds `web/site_nav.css` and `web/site_nav.js`, those two files are the whole list of notes, and anything else on it is a real difference. When the job says that an image was not compared (the base Dockerfile cannot build a tree that adds or drops a file that the build copies in), the change of that Dockerfile is read instead. When the job says that the deterministic link did not hold (an annotation on the run), the programs were not compared and only the link's inputs and the other files were.
