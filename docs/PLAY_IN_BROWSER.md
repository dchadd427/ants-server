# Play in the browser

The game runs in a modern web browser, as WebAssembly, with nothing to install: **[Play Ants Online at beta.playants.org](https://beta.playants.org)**. This page says what that site does. To build and serve it yourself, see [`BUILD_AND_RUN.md`](BUILD_AND_RUN.md). The game is developed and tested in a Chromium-based browser (the engine of Chrome and Edge); Firefox and Safari have not been tried. A phone can play it too: [`TOUCH.md`](TOUCH.md).

## Every page in one look

The changelog page (`/changelog`), the Legal page (`/legal`) and Sprites and sounds (`/asset_catalog/`) are in the Classic look of the front page, with the site's bar at the top (no logo; Home leads back to the front page). They link one stylesheet, `web/front/classic.css` (served at `/front/classic.css`: the colors, the green frame, the teal buttons, the black boxes, the footer bar of the front page; the font is beside it in `web/front/`), and add only their own rules. The front page and the game page keep inline copies of their colors. `tests/scripts/test_web_pages_classic.py` finds every page that the site serves and fails, naming the page, when one is not in the look.

**The game page** (`web/shell.html`) has the front page's look too: the clay, the thin green frame, the teal buttons, the black boxes, the game's font and the logo from `web/front/`. The loading screen shows the logo and a teal bar, and the picture sits in the same frame as the front page's pictures. The bar at the top is the site's (the documentation of the site's top bar) and the page has no footer; under the picture there is only the rematch strip, and the picture's shape and the fullscreen mouse are rows of the settings menu. Up to 700 px the bar is one row from the left edge, with no logo: **Home**, the Settings gear, **Fullscreen** and the **Menu**, whose last small link, **Reload page**, is what the Reset button was.

## Starts at once, and the sound follows your first click or key

- There is no start button. The game runs as soon as its data has downloaded (a loading card shows the download and goes away by itself); the original's own loading screen and quick help follow as always.
- Browsers let a page make sound only after you have done something on it, so the music and the sound effects begin with your first click, key press or touch on the page. The page keeps trying until the browser lets the sound run (Safari is the strictest; what each browser needs is under "Sound and the autoplay rules" below).
- The page downloads the game's data (19.3 MB) itself and tries again, up to three times, when a download fails (a browser's cache can refuse a download). If every try fails, if a file of the game (`index.js`, `index.wasm`) cannot be loaded, if the game never starts, or if the download is a web page instead of the data (a captive portal), a card with a **Reload** button replaces the loading screen.
- A box of the browser's own ("Leave the game and go back to the menu?", the copy of a recording's link) stops the page until you answer it, so the page pauses the game's sound while it is open and resumes it after; without that, the browser plays the last piece of sound over and over (`antsQuietly` in `web/shell.html`, run by `tests/scripts/web_quiet_dialog_check.js`).

**Sound and the autoplay rules.** A browser lets a page make sound only after the person has done something on it, so the game's Web Audio context (SDL's, `Module.SDL2.audioContext`, opened when the game starts) begins suspended and the game's sound and music begin the moment it is resumed; the game itself does not wait for it, and there is no start overlay any more (the page used to hide the game behind a card that said "Click anywhere to play!" until a click). SDL's own Emscripten audio already resumes the context at the first `keydown`, `mousedown` and `touchstart` (`autoResumeAudioContext`: once each, on the document and the canvas); the old page's own tries did nothing (it looked for a global `SDL2`, which does not exist, and made a second context that played nothing). `web/shell.html` now keeps trying until the context really runs (no `once`: a press that grants nothing, such as the Esc key or a shortcut of the browser, or a press before the context exists, would use the attempt up), on `pointerdown`, `mousedown`, `click`, `touchend` and `keydown`, and takes its listeners off as soon as the context runs; a context that stops later is resumed by the next press (`statechange`, `visibilitychange`). What each browser needs: *Chrome and Edge*: a context created before any user activation starts suspended; `resume()` works after a user activation (`mousedown`, `pointerdown` of a mouse, `pointerup` / `touchend` of a finger or a pen, `keydown` of a key that is not Esc or a shortcut of the browser), and the activation is sticky: after the first press anywhere on the page a context created later starts running. *Firefox*: the same rule (a suspended context, `resume()` in an input event: click, keydown, touchend; the person may also allow audio for the site, then the context runs at once). *Safari* (macOS and iOS): the strictest: `resume()` must be called inside the handler of a gesture (`click`, `touchend`, `keydown`), it is not sticky, `touchstart` does not count on iOS, a context that a phone call or the lock screen interrupted (`interrupted`) needs a new press, and the ringer switch silences Web Audio on an iPhone. The built-in browser lets pages play at once (its context was `running` before any press), so the check there exercised the page's logic with a real context that was suspended by hand: a trusted click resumed it, a second suspension was resumed by the next click, with the context running the listeners were gone (no `resume()` call), and a press while no context existed raised nothing and the next press resumed it. The keyboard focus: the canvas takes it when the game is ready, and again at the first press inside the game.

## A network match keeps playing in a hidden or minimised tab

- A browser stops drawing a page that you cannot see and slows its timers. Every message of the game server still wakes the game, which plays its turns without drawing anything and without sound or music. So the match goes on at the normal speed, nobody is told that you lag (`<your name> is lagging`), and you find it up to date when you come back (the music of a match that begins or ends meanwhile follows then). A single game (no network) simply waits while the page is hidden, as the desktop game does when minimised.
- A server that stops answering is noticed after 10 seconds of real time, a hidden page included (the page's timer is a Worker, which the browser does not slow): a seat hidden for minutes noticed a paused server at +10 s, as a shown one did.
- **Limits**: a computer that sleeps, a phone that locks its screen or leaves the browser, and a tab that the browser freezes stop the page (a frozen tab loses its connection when it wakes up). Since v0.6.0 the server holds such a seat and pauses the match; the game reconnects with the seat's key, or **Rejoin your match** takes the seat back. A seat whose page stays connected but runs no turns is still called lagging after 3 seconds and dropped after 30 ([`MULTIPLAYER.md`](MULTIPLAYER.md), "Lag, silence and drop-outs").
- No automated test covers this code, which exists only in the web build. The manual check and the opt-in script `tests/scripts/test_web_hidden.sh` are in [`NETWORK_PORT.md`](NETWORK_PORT.md#the-browser-as-a-client-hidden-tabs-and-sound-v0096), "The browser as a client: hidden tabs, and sound".

## The screen stays on

- The game page asks the browser to keep the screen awake (the Screen Wake Lock, `navigator.wakeLock`, as a video page does) while a match is played, from the countdown card to the results, and while a recording plays or a live match is watched (`web/wake_lock.js`, called by `web/shell.html`). A paused recording, its end and a file that cannot be shown do not hold it. The lock is let go on pause, at the results and when the page is left, and asked for again on play, on "Watch again", for the next match and when the tab is shown again (the browser drops it while a tab is hidden). The power button still locks a phone ([the limits of a hidden tab](#a-network-match-keeps-playing-in-a-hidden-or-minimised-tab)).
- A browser without the Screen Wake Lock (iOS before 16.4, and others) is left as it is: no message, no stand-in. A request that the browser refuses (a low battery, a power saver, a policy) or never answers is dropped without a word and asked again after 15 seconds, or when the tab is shown. The game never waits for it and nothing is drawn. Tests: [`TESTING_PYTHON.md`](TESTING_PYTHON.md).

## Your own orders show at once in a network match

- The game can run a second engine next to the match's own (the confirmed one, which the host's turns, the server's referee and every hash keep exactly as they were). An order is run on it in the same call and the screen shows it, a few ticks ahead, so the ants answer a click as they do in a game of one machine instead of one round trip, one seal and one jitter buffer later. The corner's `delay` shows what the click feels.
- **It is on by default.** The other players' ants (people and computer players) are drawn from the confirmed engine, a moment behind your own (one round trip, about), and are never corrected, so they do not jump or slide back when an order of theirs arrives. When your own ants are corrected (rarely) they slide to where the engine has them, never faster than an ant walks, instead of jumping. `?others=predicted` draws the other players' ants from the predicted engine too, as before, to find out whether a trouble is this picture's (for comparison in real matches only: **retire in v0.22.3 at the latest**). `?prediction=off` on the game page's address switches it off, as the game's `--no-prediction`; a game on one computer never predicts. Once on, it switches itself off for a while (ten seconds, twice as long each time) when its work takes too long on a slow device, and it is off in a hidden tab, in a pause and while the "Get ready" dialog is up.
- More: [`MULTIPLAYER.md`](MULTIPLAYER.md), "Prediction of your own orders"; the design: [`NETWORK_PORT.md`](NETWORK_PORT.md#prediction-of-ones-own-orders-predictionhpp-cue_routerhpp-netgame-applicationview_sim).

## The seam to a site

The game page (`web/shell.html`), the Map Maker (`web/mapmaker.html`) and the sprite and sound catalog (`asset_catalog/index.html`) are the game and its tools. A site that serves them (a counter of visits, a chat hub, the match history, the bar at the top of its pages, the Map Maker's "Connect an AI..." and "Submit for approval...") adds its own scripts and styles through **one file**, `web/site_hooks.js`; no page names another file of a site. Each page loads it twice, `<script src="site_hooks.js" data-page="NAME">`: in its head, before the stylesheets that a site adds, and where its scripts would come (after the markup that they work on).

- **The file in the tree is a stub that does nothing.** It defines `window.AntsSite` with one empty function for each thing a page tells a site (the page has started, the game is running, a game on this computer began, what the site knows of a finished match, a recording has been played for a while, the stats of the recording on show, the Map Maker is up); its comment says what each one is given. A page looks for a hook before it calls it, so a tree with the stub alone is the game and its tools: the pages work, with no bar's style, no counter, no history and no AI or sending of maps in the Map Maker (`tests/scripts/test_web_seam.py` runs this).
- **A site serves its own file in its place.** That file writes the tags of its styles (in the head) and of its scripts (at the end) with `document.write`, so that they load in order and before the page's own code, and fills in the hooks. For the Map Maker it also puts the two buttons in the top bar and gives the page's parts (the map open, the dialogs, the canvas, the store) to its own code, which loads the AI's and the sender's scripts only when a player needs them.
- The tests of a site's file read the pages as the browser builds them, with its tags written in.
